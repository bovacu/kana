kana — build commands
=====================

THE SOURCES (docs/architecture.md says what each layer is for):
  fude/drawing/   the drawing core, every app's: app/ (the shell's parts) base/ ink/ widgets/
  fude/study/     a study app's: app/ (its extension, verbs, files, flags) chars/
                  handwriting/ models/ screens/ widgets/ services/
  fude/lang/ja/   Japanese's own; fude/lang/zh/ Chinese's, fude/lang/ko/ Korean's (lang.h:
                  what a language gives)
  apps/kana/      Kana: kana.c (the shell), src/ (its own: kana_app,
                  version.h, text_ids.h), assets/, platform/ios/, tools/, docs/, site/
  apps/hanzi/     Hanzi, Kana for Chinese: hanzi.c, src/, assets/, platform/ios/, tools/
  apps/hangul/    Hangul, Kana for Korean: hangul.c, src/, assets/, platform/ios/, tools/
  tools/          the apps' shared tools: strings/, mlkit/, lectures/ (the
                  phrasebooks), icons/
  apps/draw/      Draw, the drawing app: draw.c, src/text_ids.h, assets/, tools/
Each header is beside its source and is included by its layer's path
("drawing/widgets/row.h", "study/app/study.h"); the include paths are
-I<project>/fude and the app's src/. A source added goes into the four lists
below (Windows, Android, iOS, macOS) in its folder's place.

ONCE, after the move into folders (2026-10-02): delete build/ before building —
the builder links every object it finds in its obj/ folder, and the old flat
names (src.toolbar.c.o) would be linked beside the new (fude.drawing.app.ui.c.o...).

THE TESTS: tests/run.sh (macOS or Linux; RDE beside the project, or RDE=...)
builds every suite with AddressSanitizer and UBSan and runs it; tests/README.md
has what each covers.

THE STRINGS: every text the app shows, in its five languages, is in the layers'
strings files — fude/drawing/strings.py (the core's), fude/study/strings.py (a
study app's) — and the app's own tool, which reads them and adds its own:
python3 apps/kana/tools/strings.py writes apps/kana/assets/text/strings.rdel and
apps/kana/src/text_ids.h (don't edit those by hand); apps/draw/tools/strings.py
the same for Draw. A string of the core's or the study's changed: run both.
THE FOURTH LANGUAGE is the one the app teaches (a learner may use the app in it):
Kana's Japanese; Hanzi's Chinese and Hangul's Korean, read from files beside each
layer's (fude/drawing/strings_zh.py, fude/study/strings_zh.py, fude/lang/zh/
strings_zh.py, apps/hanzi/tools/strings_zh.py; _ko for Hangul) of rows
x('ID', text). It takes Japanese's place only when every string has one (the tool
prints how many are missing), and the app then offers it with its flag
(assets/flags/cn.png, kr.png: drawn by tools/icons/flags.swift); until then those
apps keep Japanese. On the very first launch the app speaks the device's language
if it is one of its five, English otherwise.

The engine is built separately from the app, and it is built PER PLATFORM. A
Windows engine build followed by an Android app build (or the reverse) does not
work: rde_config.h and shaders.h are regenerated per platform. Build the engine
for the platform you are about to target, first.

The Android services are the apps' own Java (fude/android/java, com.rde.fude:
--android_java), reached from C through JNI (fude/drawing/base/android.h and the
*_android.c sources above). Google's ML Kit comes from Maven, pinned by the app's

ANDROID (from the Mac) — tools/android/build.sh
------------------------------------------------
The same apps, built by one script (it holds the source lists and every flag):

  zsh tools/android/build.sh engine            # RDE for Android: FIRST, after any engine
                                               # change, and after building the engine for
                                               # another platform (rde_config.h is per platform)
  zsh tools/android/build.sh kana              # or hanzi, hangul; --release for a release build
  adb install -r build/kana-android/Kana.apk   # the tablet, by USB, developer options on

--release (an engine build with --release first): build/<app>-android/<App>-release.apk,
beside the debug <App>.apk; the same key, so either installs over the other. A
low-end tablet (Galaxy Tab S6 Lite) is slow with the debug build and smooth with
the release one: judge speed on release.

GPUs: SDL's Vulkan asks by default for features some Android GPUs lack (the Tab S6
Lite's Mali-G72: depth clamping, clip distances, anisotropy) and refuses the
device; RDE then makes it again without them (logged: "GPU device made without
the optional features"). Nothing to do here; it is in the engine. A device with
no Vulkan at all cannot run RDE: the manifest requires Vulkan (Play hides the app
there), and a hand-installed APK shows "Graphics not supported" and closes.

Needs Android Studio (its JDK, the SDK at ~/Library/Android/sdk with platform and
build-tools 37 and an NDK; the newest NDK installed is used, or ANDROID_NDK=...).
The JDK is reached through build/jdk, a link without the space Android Studio's
path has (the builder runs keytool through the shell, unquoted).

THE SIGNING KEY: the first build makes build/<app>-android/com.rde.<app>.keystore
(alias and passwords: the builder's, "android"). KEEP A COPY of it outside build/:
an APK signed with another key cannot update the installed app, and Play needs the
same key for every update. The three made on 2026-10-03 are backed up in
~/kana-android-keys/ (never commit them). Building with a kept key:
  zsh tools/android/build.sh kana --android_sign_path=$HOME/kana-android-keys/com.rde.kana.keystore

THE LIBRARIES (ML Kit): apps/<app>/platform/android/deps.lock pins every Maven
artifact; the build reads it (--android_deps_file) and downloads what is missing
into build/android_deps (--android_dep_cache). To change a version, resolve again,
EVERY ROOT IN ONE COMMAND (separate runs would each pin their own tree):

  ~/RDE/builder --android_dep_cache=build/android_deps \
    --android_dep_resolve=com.google.mlkit:digital-ink-recognition:19.0.0 \
    --android_dep_resolve=com.google.mlkit:translate:17.0.3 \
    --android_dep_resolve=com.google.mlkit:text-recognition-japanese:16.0.1 \
    --android_dep_resolve=com.google.android.gms:play-services-mlkit-document-scanner:16.0.0 \
    --android_deps_out=apps/kana/platform/android/deps.lock

(text-recognition-chinese for Hanzi, -korean for Hangul.) The libraries' native
code (jni/<abi>) and model files (assets/) go into the APK with them, and their
manifests are merged.

Each app build compiles every source afresh (the builder deletes its intermediates
after packaging): a header change needs nothing special; about a minute an app.

THE EMULATOR (no tablet at hand): an AVD (Device Manager in Android Studio), then
  adb install -r build/kana-android/Kana.apk
  adb shell am start -n com.rde.kana/.KanaActivity
  adb logcat | grep -E "SDL_RDE|Fude"
Its GPU is software: ~20 frames a second, and a quick tap can begin and end
between two frames — hold taps (adb shell input swipe x y x y 200).

On Android the window is laid out in dp (rde_window_set_density_scaling, called
by fude_app_window), as iOS in points: an iPad's sizes on an Android tablet.

Android's Back (button or gesture; Escape on a computer) closes what is on top as
its own button would (fude_app_back): Settings' cards, Settings, the side panel,
the toolbar's palettes, the page's menu, then the screen on top through its row's
Back or Close; the document bar's search; a lasso selection. With nothing open it
is the system's Back (rde_mobile_system_back): the app goes to the background.

apps/kana/platform/ios/ holds what the app is on iOS besides its code: the asset catalog
(Assets.xcassets: the icon, AppIcon-1024.png, drawn from AppIcon.svg — 日本語 in
KanjiVG's strokes before a red sun, over an open book; LaunchIcon, the icon
rounded as iOS rounds it, for the launch screen; LaunchBackground, the launch
screen's colour: Paper's page, Night's in dark mode), the launch screen (LaunchScreen.storyboard:
the icon centred, 160 points) and Kana's
own Info.plist keys (Info.plist: iPad only, portrait either way up — the app locks it on Android too, app.c — full screen, no
non-exempt encryption, the camera's purpose, Kana's five languages), merged over
the engine template's; localized/<language>.lproj/InfoPlist.strings, the camera
prompt in each language, go into the app through --ios_bundle (a plain folder:
its contents are copied beside the executable) — and make the App Store list the
five languages. --ios_assets,
--ios_launch_storyboard and --ios_plist are builder options added for them
(rde_build.c); without them a build gets the template's.

ML Kit (Google's handwriting recognition, used by Check and Copy as text; and
its text recognition with the Japanese model, used by Text from photo) must be
set up ONCE before the first iOS build — and again after the tool changes — it
downloads the pinned pods and builds their sources into third_party/mlkit/
(git-ignored), no CocoaPods needed:

  python3 tools/mlkit/setup.py

--ios_framework / --ios_bundle and the iOS -L are builder options added for it
(rde_build.c). The Japanese model (~20 MB) downloads on the app's first run.

--apple_development_name WITHOUT the "Apple Development: " prefix — the builder
adds it. --ios_package_name must match the profile's app id (com.rde.kana). The
profile is a free-team one and EXPIRES AFTER 7 DAYS: regenerate it in Xcode with
the iPad connected, then point the command at the new file.

Install and launch (devicectl installs the .app, not the .ipa):

  unzip -o build/kana/Kana.ipa -d /tmp/kana_ipa
  xcrun devicectl device install app --device <UDID> /tmp/kana_ipa/Payload/Kana.app
  xcrun devicectl device process launch --device <UDID> --terminate-existing com.rde.kana

`xcrun devicectl list devices` shows the UDID. First launch on a device needs
Settings > General > VPN & Device Management > trust the developer.

A RELEASE BUILD TAKES NO ARGUMENTS: whatever it is launched with is ignored, by
Kana and by RDE — users cannot change how it behaves. Debug builds read them
(the look flags below, --perf, the bake). To measure a release, build it with
-DKANA_ALLOW_ARGS added to the command (after -Wall -Wextra); never ship that one.

Measuring a build on the device (the iPad unlocked): launch it on a screen
with --perf=SECONDS — frame times are appended to perf.txt in its save folder,
then copied back (--browse, --kana, --album, --stats, --exam: those screens;
no screen flag: the page):

  xcrun devicectl device process launch --device <UDID> --terminate-existing com.rde.kana --browse --perf=8
  xcrun devicectl device copy from --device <UDID> --domain-type appDataContainer --domain-identifier com.rde.kana \
      --user mobile --source "Library/Application Support/rde/engine/kana/perf.txt" --destination perf.txt

The release build (--release instead of --debug, with the engine built
--release for iOS too) on the iPad mini 6, 2026-10-01: every screen 59.9 fps,
Kana's render 1.5-5.4 ms a frame.

If the builder was just rebuilt (rde_build.c changed), the FIRST run can fail on
the name's spaces/parentheses — it re-runs itself unquoted. Run it again.

THE CHARACTER DATA BAKE
-----------------------
apps/kana/assets/data/characters.kana is BAKED from KanjiVG + KANJIDIC2, with the
JLPT lists, JMdict's example words and Tatoeba's example sentences (format in
fude/study/chars/kanji.h; the bake: fude/lang/ja/bake.c). Re-bake only when the sources are updated. The sources are
not in the repository (data/raw/ is ignored):

  mkdir -p data/raw && cd data/raw
  curl -L -o kanjivg.xml.gz https://github.com/KanjiVG/kanjivg/releases/download/r20250816/kanjivg-20250816.xml.gz
  curl -L -o kanjidic2.xml.gz http://www.edrdg.org/kanjidic/kanjidic2.xml.gz
  curl -L -o JMdict.gz http://ftp.edrdg.org/pub/Nihongo/JMdict.gz
  curl -L -o JMdict_e.gz http://ftp.edrdg.org/pub/Nihongo/JMdict_e.gz
  gunzip -k kanjivg.xml.gz kanjidic2.xml.gz
  gunzip -c JMdict.gz > JMdict.xml
  gunzip -c JMdict_e.gz > JMdict_e.xml
  mkdir -p jlpt
  for n in 1 2 3 4 5; do
    curl -L -o jlpt/n$n-kanji-char-eng.mem http://www.tanos.co.uk/jlpt/jlpt$n/kanji/n$n-kanji-char-eng.mem
  done
  mkdir -p tatoeba && cd tatoeba
  for l in jpn eng spa fra por; do
    curl -L https://downloads.tatoeba.org/exports/per_language/$l/${l}_sentences.tsv.bz2 | bunzip2 > ${l}_sentences.tsv
  done
  for p in jpn-eng jpn-spa jpn-fra jpn-por; do
    curl -L https://downloads.tatoeba.org/exports/per_language/jpn/${p}_links.tsv.bz2 | bunzip2 > ${p}_links.tsv
  done
  curl -L https://downloads.tatoeba.org/exports/jpn_indices.tar.bz2 | tar xj
  cd ../../..

(The JLPT files are Jonathan Waller's N5-N1 kanji lists as Mnemosyne decks,
CC BY; the bake reads the kanji out of them. JMdict is EDRDG's Japanese
dictionary, CC BY-SA 4.0 like KANJIDIC2; the bake keeps up to twenty words a
kanji (six of them its examples). The FULL JMdict (JMdict.xml) is what the bake
reads when it is there: its English, and the Spanish and French glosses for
the other languages (it has no Portuguese: those words stay English). Without
it, JMdict_e (English only) — then the words have no other languages. Kanji
meanings in Spanish, Portuguese and French come from KANJIDIC2. JMdict is
updated daily: a re-bake picks up whatever the download has. Tatoeba's
sentences are CC BY 2.0 FR: the bake keeps one per word — a Japanese sentence
of a comfortable length with the word in it and an English translation, and
the Spanish, French and Portuguese ones when Tatoeba has them; ~1.6 MB.
jpn_indices.csv, Tatoeba's word index, says which word a sentence has (行 read
ぎょう or the 行 of 行く): without it the words are found as text, more loosely. The
English file is large (~110 MB): the bake reads it whole, outside RDE's memory
pool. Without data/raw/tatoeba/ the file has no sentences and the viewer shows
none.)

Then, with the Mac desktop build above, from the project root:

  ./build/kana/osx-silicon/debug/project/exe/runnable --bake
      [--kanjivg=PATH] [--kanjidic=PATH] [--jlpt=DIR] [--jmdict=PATH] [--tatoeba=DIR] [--out=PATH]

It reports characters, strokes, sizes, stroke-count disagreements and example
words and sentences, then the look-alikes (the matcher over the file just
written, appended as 'LOOK': ~18 s), and takes about twenty-five seconds. The sources are CC BY-SA and CC BY: apps/kana/assets/data/LICENSE-data.txt must
ship with the app and its attribution must be shown to users.

WHAT TO LOOK FOR ON THE DEVICE
------------------------------
1. The top line of the HUD. "PEN" means stylus events arrive and the shared-ink
   plan holds. "TOUCH ONLY" on an iPad with an Apple Pencil is the answer to
   open question 1 in apps/kana/docs/design.md, and it is a bad one.

2. Pressure moving as you press harder, and the stroke visibly thickening. If
   pressure stays 0.00 the PEN_AXIS events are not arriving even though position
   is — a different failure from no pen at all, and worth knowing apart.

3. INPUT HZ while drawing continuously. A pen sampling at 120-240 Hz that shows
   ~60 here is being coalesced to the frame rate: fast strokes will come out as
   visible polygons however low the lag is. Press M and draw fast — evenly
   spaced dots mean the full rate is arriving, long gaps on the quick parts mean
   it is not.

4. THE GAP. Press H to hide the HUD, draw a fast circle, and look at the
   distance between the nib and the end of the ink. That distance IS the latency
   and it is the only honest measure of it — the numbers on screen cover the
   app's half only, because everything before the event reaches the process is
   invisible from inside it. Photograph it if you want a number: gap in mm,
   divided by pen speed in mm/ms.
